## 3절. 데이터 설계

### 3-1. Supabase 표 초안

원칙: **사람 한 명의 행동을 한 줄씩 쌓지 않고, "날짜 × 항목" 묶음 칸에 숫자 +1** 한다(행 수가 작고, 개인정보가 안 남음). 더하기는 DB 함수(RPC) 1회 호출로 끝낸다.

|---|---|---|---|

| `calc_runs_daily` | day, process(wallpaper/flooring/mortar/tile), mode(quick/precise), py_bucket(20·30·…·na), region, runs | (day, process, mode, py_bucket, region) | 계산기 통계 |

| `post_likes` | slug, likes | slug | 좋아요 누적 (Upstash `likes:*` 대체) |

| `site_settings` | key, value(jsonb), updated_at | key | 광고 스위치 등 |
| `kakao_members` (선택) | kakao_id 해시, nickname, first_seen, last_seen | kakao_id 해시 | 카카오 회원 목록 |

권한: 위 표 전부 RLS 켜고 공개 읽기 정책 없음. 쓰기·읽기는 서버의 서비스 롤 키로만. 더하기 함수(`inc_page_view` 등)는 `ask_inc_view`와 같은 방식(`security definer`, anon 권한 회수).

### 3-2. Redis → Supabase 이전

| 지금 (Upstash) | 바뀐 뒤 (Supabase) | 호출 수 |
|---|---|---|
| `views:{slug}` INCR + `likes` GET 2회 | `inc_page_view(path, region, device)` 1회가 누적 조회수·좋아요 숫자를 같이 돌려줌 | 글 1회 열람 = DB 호출 1 |
| `calc:run:*` 6명령 | `inc_calc_run(...)` 1회 (`after()`로 응답 뒤) | 1 |
| `contact:click:*` 2명령 | `inc_contact_click(...)` 1회 | 1 |
| `likes:{slug}` INCR/DECR | `post_likes` 더하기·빼기 함수 1회 | 1 |
| `rl:*` 로그인 제한, `auth:diag`, keepalive | 형아 결정: (가) 그대로 Upstash(월 수천 건) (나) Supabase 표 `rate_limits`로 이전 | — |
| GA 리포트 봇의 Upstash 읽기 | Supabase 일별 표를 읽도록 수정 + 타일 추가 | — |

이전 순서: 새 표·함수 만들기 → 쓰기를 Supabase로 바꾸기(이때부터 Upstash 쓰기 0) → Upstash 한도가 리셋된 뒤 **남은 `views:*`·`likes:*`·`calc:run:*` 값을 1회 읽어 옮김**(누적 조회수는 `page_views_daily`에 "이전분" 한 줄로) → Upstash 쓰기 코드 삭제.
Supabase 무료 단계는 요청 횟수 제한이 없고(용량 500MB·전송량 제한만), 일별 묶음 표는 하루 수백~수천 줄 수준이라 여유가 크다.

### 3-3. 지역 판정 규칙

| 순서 | 출처 | 값 | 비고 |
|---|---|---|---|
| 1 | 사용자가 고른 지역 ("우리 동네" 칩, 브라우저에 저장) | 시도 코드 (+ 시군구) | 광고 명세 3.2 "사용자 선택값 우선" |
| 2 | `x-vercel-ip-country` | KR 아니면 → `ZZ`(해외) | |
| 3 | `x-vercel-ip-country-region` | ISO 시도 번호 → 시도 코드 | 아래 표 |
| 4 | `x-vercel-ip-city` (URL 인코딩된 영문 도시명) | 시군구 참고값 | **통계용 참고만. 배너 선택 기준으로 쓰지 않음** |
| 5 | 아무것도 없음 | `00`(전국) | |

시도 번호 대응: 11 서울 · 26 부산 · 27 대구 · 28 인천 · 29 광주 · 30 대전 · 31 울산 · 50 세종 · 41 경기 · 42/51 강원 · 43 충북 · 44 충남 · 45/52 전북 · 46 전남 · 47 경북 · 48 경남 · 49 제주 (강원·전북은 특별자치도 전환으로 옛·새 번호 둘 다 받음).

주의: 휴대폰 데이터망 접속은 통신사 관문 위치(주로 서울·수도권)로 잡히는 경우가 많아 **IP 지역은 시도 단위도 틀릴 수 있고 시군구는 신뢰하기 어렵다**. 그래서 판매 단위는 시도, 시군구 배너는 사용자가 고른 지역일 때만 쓰는 것을 권장. IP 원문은 저장하지 않는다.

### 3-4. 배너 선택 규칙

```
슬롯 요청(AD-H 등, AD-P면 공정) + 지역(3-3 결과)
 → 1) 기간 안·켜짐·그 슬롯·그 지역(시군구 일치 > 시도 일치) 배너
 → 2) 없으면 같은 조건의 "전국" 배너
 → 3) 없으면 애드센스 슬롯 ID 있으면 애드센스
 → 4) 없으면 기존 폴백: AD-H/AD-R = House Ad, AD-P/AD-F = 접힘
 여러 개면 weight 비율로 돌림. 견적 결과 값은 절대 보지 않음(명세 §6.1).
 광고 전체 스위치(site_settings) 꺼지면 전부 접힘(지금 ADS_ENABLED와 같은 동작).
```

구현 방식: 페이지마다 `/api/ad?slots=AD-H,AD-R,AD-P:철거…` **한 번** 호출 → 서버가 헤더로 지역 판정 → 서버 메모리에 5분 캐시해 둔 "켜진 배너 목록"에서 고름 → 응답. 기존 `AdSlot.tsx`의 틀(규격·라벨·House Ad)은 그대로 두고 내용만 이 응답으로 채운다. 블로그 글 화면은 정적 생성(ISR)을 유지해야 하므로 서버 렌더에서 헤더를 읽지 않는다.

### 3-5. 노출·클릭 집계 (요청 아끼는 방식)

| 항목 | 방식 | 호출 |
|---|---|---|
| 노출 | `/api/ad`가 배너를 골라 줄 때 고른 배너들을 `inc_ad_stats(day, [배너들], region, 'imp')` 1회로 한꺼번에 +1 (`after()`로 응답 뒤) | 페이지당 1 |
| 클릭 | 배너 링크를 `/go/ad/{배너id}`로 감싸서 +1 후 광고주 주소로 이동 | 클릭당 1 |
| 봇 거르기 | 사용자 에이전트에 bot·crawler·spider 들어가면 세지 않음 | — |
| 보관 | 일별 묶음만 영구 보관, 원본 행동 기록 없음 | — |
| 정산 | 월 단위로 `ad_stats_daily` 합산 → `ad_settlements` 메모와 같이 보기 | — |

GA4 쪽 호출: 관리자 화면에서만 부르고, 같은 질문은 30분 캐시(또는 Supabase `ga_cache` 표). GA4 무료 할당(속성당 하루 수만 토큰)을 넘을 일 없음.

### 1단계 추천

1-a(카운터 Supabase 이전) → 1-b(관리자 쿠키) → 1-c(대시보드) → 1-d(GA 상세) → 1-e(리포트 봇) 순. 합계 약 3.5일. 1-a를 먼저 해야 오늘부터 지역·기기 칸이 쌓이기 시작해 2·3단계 화면과 광고 영업 자료("이 지역 최근 30일 몇 명")가 채워진다.
